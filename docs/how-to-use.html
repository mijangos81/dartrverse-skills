dartR Function Review

One Claude Code command reviews one gl.* function end to end. The review is advisory — nothing in the code changes until you approve each specific finding, and nothing is pushed until you OK the commit on screen.

Running a review

any team member
1

Install the skill once

Requires Claude Code. Clone and symlink — updates arrive with git pull:

git clone https://github.com/mijangos81/dartrverse-skills.git
ln -s "$(pwd)/dartrverse-skills/skills/dartr-function-review" ~/.claude/skills/

Verify: start Claude Code in a package checkout and type review gl.report.callrate — the skill should announce itself. (The repo is private until it moves to green-striped-gecko; ask Luis for access.)

2

Start a review

Open Claude Code inside the package checkout, on your dev_<name> branch synced with origin/dev. Then just ask:

review gl.report.heterozygosity
next function in the manifest

Claude claims the function in function-review/manifest.csv (and stops if someone else already has it), so no two people review the same function.

3

Wait while Phase A runs — it touches nothing

  • Baseline first: a characterization test snapshots what the function does today, bugs included, into tests/testthat/.
  • Two verdicts: Standards (is it built right? — checked against 48 numbered conventions) and Spec (does behaviour match the docs and the function's name? — tested empirically on reference data).
  • Full report written to function-review/reports/<package>/<function>.md.
4

Read the findings, tick what you approve your call

You get the two verdicts, a plain-language findings table, and clickable approval boxes — all in one turn. Example (abridged from the gl.report.callrate trial):

Which changes should be applied?

Free text always works too: “apply 2 and 3, defer 1”, “3 but only the guard, not the rename”.

Escalation gate. Anything that changes an argument's meaning or default, numerical output, or a function's signature sits in its own box, worded as the consequence — you approve “results change”, not just “fix the bug”. It also triggers a caller grep across sibling dartR.* packages and a NEWS entry.
5

Phase C applies only what you ticked

The characterization test re-runs: every diff from baseline must map to an approved finding — an unexplained diff stops the process. Problems discovered mid-fix are not patched opportunistically; they come back to you as a one-line addendum ask.

6

OK the commit, then the PR opens your call

The full commit message and PR title are printed on screen and nothing is pushed until you reply. Then: one function per PR, from your branch to dev, report linked in the body, manifest set to pr-open.

Custodian flow

package maintainer / campaign lead
7

Review and merge the PR

Each PR carries one function, its linked report, and the characterization test as regression evidence. Check that behaviour-changing findings were approved as consequences (they are recorded verbatim in the report's Approval section), then merge to dev. After merge, the manifest row flips to done.

8

Ratify the proposed conventions

34 of the 48 rules are [confirmed] and enforced; 14 are [proposed] and only ever produce advisory findings until the team ratifies them. The consequential ones: plot-saving idiom (PLT2), back-compatibility policy (API1–3), snapshot-before-modify (TST2–3), FBM-awareness (DAT6). Reply per rule via a GitHub issue titled with its ID, e.g. DAT6: too strict for gl.dist.*.

9

Turn bad findings into fixtures

False positives and missed defects are the most valuable feedback — they become entries in references/fixtures.md, the set of known historical bugs the skill must keep finding. Any edit to the skill or the conventions requires a re-run on one fixture plus a version bump before it merges.

Quick reference

Say to Claude Code

  • review <function>
  • next function in the manifest
  • apply 1 and 3, defer the rest

Where things live

  • function-review/manifest.csv — claims + status
  • function-review/reports/ — full reports
  • tests/testthat/test-<fn>.R — baselines
  • references/dartr-conventions.md — the 48 rules

Severities

  • BLOCKER / HIGH — wrong results or user-visible failure
  • MEDIUM / LOW — guards, conventions, docs
  • INFO — worth knowing, no change proposed
